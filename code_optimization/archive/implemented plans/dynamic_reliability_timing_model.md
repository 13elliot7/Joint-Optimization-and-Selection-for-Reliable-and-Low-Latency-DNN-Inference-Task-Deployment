# 多 DNN 动态可靠性时序运行的简化建模方案

## 1. 背景与简化目标

在完整的动态可靠性建模中，多 DNN 系统通常需要同时描述：

1. DNN 在线到达
2. 子任务级执行推进
3. 链路传输推进
4. 节点与链路资源逐时释放
5. 节点与链路可靠性逐时演化
6. 运行过程中故障、恢复与重调度


这类模型表达能力强，但实现复杂度高，尤其在当前代码基础上会引入完整的任务执行器、链路事件队列和多层状态机，超出了第一阶段建模的必要复杂度。

因此，在保留“动态可靠性”主线的前提下，把多 DNN 时序运行简化为**离散时间、顺序接纳、块级执行**框架，使前序 DNN 仍然能够通过资源占用、负载与热度影响后续 DNN，但不需要做完整的任务级运行仿真。

第一版模型同时实现：

1. 节点动态可靠性
2. 链路基础可靠性建模
3. 基于当前系统状态的多 DNN 顺序接纳

但不展开传输级事件仿真，不引入节点可用性，不实现运行中迁移与重调度。

## 2. 基本思想

1. 不模拟子任务级状态机，只保留 DNN 级状态。
2. 不逐时刻推进每条传输和每个子任务，只把一个 DNN 看作一个占用若干节点资源并持续若干时隙的运行实体。
3. 一个 DNN 的运行时长不通过事件仿真获得，而是继续使用原始算法中的静态关键路径时延估计作为其执行时长代理。
4. 系统按离散时隙推进。每个时隙只做：释放已完成 DNN、统计当前占用、刷新动态可靠性、接纳一个新 DNN。
5. 节点默认始终在线，不单独建模节点可用性。
6. 第一版同时保留节点动态可靠性和链路基础可靠性，但链路只做路径级聚合，不做逐包排队和重传仿真。


该方案的目标不是完全复刻真实在线执行过程，而是在较低复杂度下，使系统能够体现以下动态特征：

- 已运行 DNN 会持续占用资源
- 热点节点和热点链路会因负载和热度而可靠性下降
- 后续 DNN 的部署决策依赖当前系统状态
- DNN 完成后资源释放，节点和链路状态可以逐步恢复

## 3. 系统状态与简化状态机

### 3.1 DNN 级状态

每个 DNN 仅保留以下状态：

- `waiting`：已到达，等待部署
- `running`：已接纳，正在占用资源运行
- `finished`：运行完成
- `rejected`：当前时刻无法接纳

### 3.2 运行中 DNN 的最小描述

对于每个 `running` 的 DNN，仅维护下列信息：

- `dnn_id`
- `assignment`
- `arrival_time`
- `start_time`
- `estimated_runtime`
- `remaining_slots`
- `used_nodes`
- `used_links`


其中：

- `assignment`：子任务到节点的部署结果
- `estimated_runtime`：当前部署下的估计运行时长
- `remaining_slots`：按离散时隙量化后的剩余运行时间
- `used_nodes`：承载该 DNN 的唯一节点集合
- `used_links`：该 DNN 的输入上传、任务间依赖传输、输出回传实际经过的唯一链路集合

## 4. 离散时序推进框架

系统采用离散时隙推进，记时刻为：

`t = 0, 1, 2, ...`

每个时刻按固定顺序执行以下步骤。

### 4.1 释放已完成 DNN

检查所有 `running` DNN：

- 若 `remaining_slots == 0`，则将其标记为 `finished`
- 释放其占用的节点资源
- 释放其占用的链路资源统计影响

### 4.2 更新当前运行状态

对于所有仍在运行的 DNN：

- `remaining_slots -= 1`

这一步不展开子任务执行推进，而是将整个 DNN 视为一个持续运行的块级实体。

### 4.3 统计当前系统负载

根据所有 `running` DNN 的部署结果，统计：

- 每个节点的总 CPU 占用
- 每条链路的总带宽占用

定义节点当前负载率：

`rho_j(t) = used_cpu_j(t) / max_cpu_j`

定义链路当前负载率：

`eta_uv(t) = used_bw_uv(t) / max_bw_uv`

第一版链路负载的估计保持基础化：

1. 不做逐包级别仿真
2. 不做链路抢占与重传
3. 对于运行中的每个 DNN，只要使用某条链路，就按预设权重或该依赖数据量对链路占用做累计

### 4.4 更新热度状态

节点热度更新为：

`h_j(t+1) = lambda_h * h_j(t) + rho_j(t)`

链路热度更新为：

`g_uv(t+1) = lambda_g * g_uv(t) + eta_uv(t)`

其中：

- `lambda_h in [0,1)` 为节点热度恢复系数
- `lambda_g in [0,1)` 为链路热度恢复系数

这意味着：

- 节点或链路被持续占用时，热度累积
- 长时间空闲时，热度逐步衰减

### 4.5 刷新动态可靠性

基于当前负载与热度，同时更新节点动态可靠性和链路动态可靠性。

### 4.6 接纳一个新 DNN

在当前时刻，取一个新到达 DNN 进入部署流程：

1. 生成候选部署方案
2. 检查资源和时延可行性
3. 用当前动态可靠性计算候选方案得分
4. 选择一个最优可行方案
5. 若成功，则加入 `running`
6. 若失败，则标记为 `rejected`

该时刻只接纳一个新 DNN，从而避免模型同时处理多个新到达事件的复杂性。

## 5. 时延建模的简化方式

### 5.1 继续复用原始静态时延模型

原算法中，一个 DNN 的总时延由以下几部分组成：

1. 输入上传时延
2. DAG 内关键路径上的计算与传输时延
3. 输出回传时延

当前代码中的时延计算由以下函数完成：

- `count_delay_random()`
- `count_delay()`

它们本质上都在计算给定部署方案下的静态关键路径时延。

### 5.2 将静态时延转为运行时长代理

在简化动态模型中，不再逐时刻模拟子任务和链路推进，而是直接令：

`estimated_runtime = estimated_delay(plan)`

然后按固定时隙长度 `delta_t` 离散化：

`remaining_slots = ceil(estimated_runtime / delta_t)`

这样，一个 DNN 一旦部署成功，就会在后续 `remaining_slots` 个时隙中持续占用其所需节点和链路资源。

### 5.3 DAG 在简化模型中的作用

即使不做子任务级执行仿真，DNN 的 DAG 结构仍然通过原始时延估计起作用：

1. 决定关键路径长度
2. 决定跨节点依赖传输量
3. 决定不同部署方案的时延差异
4. 决定该 DNN 将占用哪些路径链路


因此，DAG 的影响仍然保留在部署评价阶段，只是被折叠进 `estimated_runtime` 和 `used_links` 中，而不再展开为动态执行事件。

## 6. 动态可靠性建模

### 6.1 静态先验

保留当前节点静态先验：

- 节点运行可靠性基线：`o_j^0`
- 节点精度可靠性基线：`a_j^0`

同时为每条链路定义静态先验：

- 链路可靠性基线：`l_uv^0`

基础链路先验推荐按链路类别和带宽映射得到：

1. 同节点内部虚拟链路取 `1.0`
2. 边缘到边缘链路映射到较高可靠性区间，例如 `[0.95, 0.99]`
3. 边缘到云链路映射到略低可靠性区间，例如 `[0.90, 0.97]`

这样在缺少真实链路可靠性标签时，仍可为第一版模型提供可比较的链路先验。

### 6.2 节点动态可靠性

第一版建议只使用节点负载率与热度，得到：

`o_j(t) = clip(o_j^0 * exp(-alpha_r * rho_j(t) - beta_r * h_j(t)), o_min, o_j^0)`

`a_j(t) = clip(a_j^0 * exp(-alpha_a * rho_j(t) - beta_a * h_j(t)), a_min, a_j^0)`

其中：

- `alpha_r, beta_r > 0`
- `alpha_a, beta_a > 0`
- `clip(x, low, high)` 将数值限制在 `[low, high]`

这组公式表达：

- 当前负载越高，节点运行和精度越不稳定
- 历史热度越大，节点健康状况越差
- 节点空闲后，热度衰减，可靠性逐步恢复

### 6.3 链路动态可靠性

第一版直接引入基础链路动态可靠性：

`l_uv(t) = clip(l_uv^0 * exp(-alpha_l * eta_uv(t) - beta_l * g_uv(t)), l_min, l_uv^0)`

其中：

- `eta_uv(t)` 为链路当前负载率
- `g_uv(t)` 为链路热度
- `alpha_l, beta_l > 0`
- `l_min` 为链路可靠性下界

该模型只反映链路层面的基础退化：

1. 链路被更多运行中 DNN 共享时，可靠性下降
2. 长时间高占用的链路会因热度累积而进一步退化
3. 链路空闲时，热度逐步衰减，可靠性回升

对于某个 DNN 的路径链路集合 `E_m`，其路径级链路可靠性定义为：

`L_m(t) = prod_{e in E_m} l_e(t)`

## 7. 端到端可靠性指标

### 7.1 唯一节点和唯一链路集合

对于给定 DNN 的部署方案，定义：

- `N_m`：承载该 DNN 至少一个子任务的唯一节点集合
- `E_m`：该 DNN 实际使用的唯一链路集合

为避免原模型中“同一节点被多个子任务重复连乘”的问题，端到端运行可靠性应按唯一节点集合和唯一链路集合聚合。

### 7.2 动态运行可靠性

动态运行可靠性定义为：

`R_m^run(t) = prod_{j in N_m} o_j(t) * prod_{e in E_m} l_e(t)`

### 7.3 动态精度可靠性

定义节点 `j` 上承载任务的计算量权重：

`w_j = (sum_{i in T_m(j)} float_i) / (sum_k float_k)`

则动态精度可靠性定义为：

`R_m^acc(t) = prod_{j in N_m} a_j(t)^{w_j}`

这种写法保留了“一个节点上部署更多任务会积累精度影响”的特征，但避免了简单按任务数重复连乘。

### 7.4 总可靠性

若需要单一总可靠性指标，推荐使用：

`R_m(t) = R_m^run(t) * R_m^acc(t)`

该定义表示：一个 DNN 既要稳定运行，又要保持精度，二者共同决定其整体可靠性表现。

## 8. 新 DNN 的接纳与部署流程

在每个时刻 `t`，对一个新到达 DNN 执行如下流程：

### 8.1 候选方案生成

候选方案生成仍沿用原算法框架：

- 主算法：种群初始化、交叉、变异
- 随机基线：随机生成可行部署
- 最大资源基线：优先选择剩余资源更多的节点
- 本地优先基线：优先选择更近或更高带宽节点

因此，当前代码中已有的部署搜索框架不需要推倒重来，只需要替换评价口径。

### 8.2 可行性检查

每个候选方案仍需检查：

1. 当前剩余节点资源是否足够
2. 关键路径时延是否满足约束

其中时延检查继续使用静态估计函数。

### 8.3 动态指标评估

对于当前时刻 `t` 的候选方案，计算：

- `R_m^run(t)`
- `R_m^acc(t)`
- `Delay_m^{est}(t)`

然后将它们作为部署决策的评价依据。

### 8.4 接纳成功后的处理

若存在可行方案：

1. 记录其部署结果 `assignment`
2. 计算 `estimated_runtime`
3. 转换为 `remaining_slots`
4. 提取 `used_nodes`
5. 提取 `used_links`
6. 将该 DNN 加入 `running` 集合

若不存在可行方案：

- 该 DNN 记为 `rejected`

## 9. 指标输出与实验解释

在这套简化模型下，建议统一输出以下指标：

1. 平均接纳时动态运行可靠性
2. 平均接纳时动态精度可靠性
3. 平均估计时延
4. DNN 拒绝率
5. 节点平均负载率
6. 链路平均负载率
7. 节点与链路热度演化曲线
8. 随 DNN 到达顺序变化的可靠性衰减曲线

需要注意的是，这里的时延指标是“接纳时估计时延”，而不是逐任务仿真得到的真实完成时间。因此，本方案更适合作为：

- 第一版动态可靠性建模方案
- 论文中的简化系统模型
- 后续完整运行仿真的过渡版本

## 10. 实现顺序

1. 增加 `running DNN` 集合及其最小状态字段
2. 增加时隙推进逻辑：释放完成 DNN、扣减剩余时隙、统计当前占用
3. 增加节点与链路负载率、热度更新
4. 增加节点与链路动态可靠性计算
5. 将原始部署算法中的静态 `count_accuracy()` / `count_operation()` 替换为动态指标计算
6. 若第一版稳定后，再增强链路负载估计和路径级占用模型

## 11. 总结

该简化方案在不引入完整运行时仿真的前提下，为多 DNN 动态可靠性建模提供了一条可落地路径：

1. 保留原始 DNN DAG 对关键路径时延的影响
2. 保留多 DNN 在时间轴上的资源竞争
3. 通过节点负载率、链路负载率和热度引入动态可靠性演化
4. 通过离散时隙运行让前序 DNN 对后序 DNN 持续产生影响
5. 避免一次性进入过于复杂的子任务级事件仿真
