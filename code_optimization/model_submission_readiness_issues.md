# 当前模型待修复问题与投稿就绪整改清单

> 审查对象：抽象 DNN DAG 在云—边—端环境中的四目标部署模型与定制化遗传算法  
> 当前语义版本：`stability_fidelity_v2_return_energy`  
> 文档性质：代码整改、模型论证和投稿实验的统一待办清单  
> 审查日期：2026-07-23

## 1. 总体结论

当前项目已经形成完整且可运行的研究原型：

- DNN 推理请求被抽象为 DAG；
- 决策变量是 DAG 子任务到异构节点的部署映射；
- 优化目标统一为推理保真性、运行稳定性、时延满意度和能耗满意度；
- OSS 已按唯一节点域和唯一物理链路域分层聚合；
- IFS 已按节点承载 FLOPs 加权聚合；
- 输入上传、DAG 中间传输和结果回传已纳入链路占用与能耗；
- 定制化遗传算法、基线、指标导出和实验脚本已经贯通。

但是，当前版本仍不宜直接作为高水平论文的最终投稿版本。主要原因不是算法流程缺失，而是以下三类证据还不充分：

1. **候选评价的状态与时间语义尚未完全闭环**；
2. **IFS 的构念效度以及 OSS/IFS 的区分效度尚未被证明**；
3. **新版模型的统计实验、参数依据和可复现材料尚未形成完整证据链**。

建议按本文的 P0、P1、P2 顺序整改。完成全部 P0 后，模型才具备稳定投稿的基本条件；P1 决定论文能否经受模型合理性和实验充分性的严格审稿。

## 2. 严重级别

| 级别 | 含义 | 投稿前要求 |
| --- | --- | --- |
| P0 | 影响核心结论、模型自洽性或实验有效性 | 必须修复 |

## 3. 当前不再属于待修复项的内容

下列问题在当前语义版本中已经处理，不应继续写入“未解决问题”：

- OSS 不再采用随组件数量快速衰减的节点—链路原始连乘作为主优化值；
- 双向有向边已经映射到共享的物理链路故障域；
- 结果回传已经纳入时延、候选链路占用、OSS 和能耗的通信边界；
- 能耗已统一转换为“越大越好”的满意度，且保留原始总能耗用于审计；
- 候选 OSS/IFS 预测不会直接修改环境真实状态；
- 默认拓扑的节点当前质量值与其基础先验值已使用同一次采样结果；
- `raw_joint_product` 仅作为诊断量保留，不能再解释为本次 DNN 推理成功概率。

此外，以下设计选择本身并非错误，但必须明确研究边界：

- **使用抽象 DAG 而不建模具体 DNN 网络是合理的**，但不能据此宣称获得了具体模型在真实数据集上的准确率提升；
- **能耗不随候选负载动态预测可以接受**，前提是明确采用“计算操作和传输数据量决定能耗”的确定性一阶模型；
- **使用经验先验可以接受**，但先验来源、范围和敏感性必须可解释、可复现。

## 4. P0：投稿前必须修复

### P0-01 候选四目标没有基于同一个预测状态计算

**当前表现**

`proposed.py::_evaluate_assignment()` 的顺序是：

```text
使用当前有效带宽估计 delay
  → 使用该 delay 预测候选节点/链路负载
  → 预测 OSS 和 IFS
  → 根据部署计算确定性能耗
```

因此：

- OSS/IFS 表示候选接纳后的预测质量；
- delay 主要表示候选接纳前、当前网络状态下的估计；
- energy 表示不依赖动态状态的部署级确定性估计。

这不是完全错误，但论文若将四者统称为“候选部署后的性能”，时间语义并不一致。

**代码依据**

- `proposed.py:333-373`
- `core/environment.py:383-423`
- `core/environment.py:683-761`

**影响**

- 候选流量使链路负载升高后，有效带宽会降低，但时延没有据此重算；
- 时延目标可能系统性高估高通信量候选；
- delay、OSS 和链路约束可能评价的不是同一个候选状态；
- 审稿人可能认为动态可靠性模型和时延模型只是串联调用，而非统一系统模型。

**推荐修复**

新增不修改真实环境的统一预测快照，例如：

```text
CandidateStateSnapshot
  assignment
  predicted_runtime
  predicted_node_loads
  predicted_link_offered_rates
  predicted_link_loads
  predicted_node_heat
  predicted_link_heat
  predicted_effective_bandwidths
  predicted_oss
  predicted_ifs
  predicted_delay
  deterministic_energy
```

在单个候选内部执行有限次不动点迭代：

```text
用当前有效带宽初始化 delay
  → 根据 delay 计算候选流量速率
  → 汇总“现有运行任务 + 候选任务”的链路 offered rate
  → 计算预测负载、热度和有效带宽
  → 用预测有效带宽重算 delay
  → 直至收敛或达到最大迭代次数
```

建议默认：

- 最大迭代次数：5；
- 相对时延变化阈值：`1e-4`；
- 未收敛时保守采用迭代过程中最大的时延；
- 路由在该过程内保持固定，避免把动态路由同时引入核心模型。

**验收标准**

- `_evaluate_assignment()` 只消费一个统一的候选快照；
- delay、链路负载、OSS 和链路约束来自同一组预测有效带宽；
- 候选预测过程不修改环境状态；
- 零候选流量时，预测值退化为当前状态值；
- 增大候选通信量时，预测链路负载不下降、预测时延不下降；
- 固定随机种子下结果可复现。

### P0-02 候选链路预测与接纳后的真实链路状态更新公式不一致

**当前表现**

候选预测采用：

```text
predicted_load
  = current_load_ratio
  + candidate_data / runtime / current_effective_bandwidth
```

真实状态推进则重新汇总所有运行 DNN 的数据速率，再除以当时的有效带宽：

```text
actual_load
  = sum(all_running_data / stored_runtime)
  / current_effective_bandwidth
```

`current_load_ratio` 是在旧有效带宽下归一化的结果。直接在其上叠加候选归一化负载，在有效带宽变化时不等价于重新汇总 offered rate。

**代码依据**

- 候选预测：`core/environment.py:411-423`
- 真实更新：`core/environment.py:update_link_loads()`
- 候选注册后立即重算资源：`core/environment.py:787-811`

**影响**

- 优化器看到的候选链路负载可能不等于候选实际接纳后的链路负载；
- 链路 OSS、超载约束和预测时延均可能产生偏差；
- 预测模型无法通过“预测值—下一时隙实际值”一致性测试。

**推荐修复**

不要叠加归一化后的 `load_ratio`，改为统一维护或即时重建链路 offered rate：

```text
existing_rate_l
  = sum(data_of_running_dnn_on_l / running_dnn_runtime)

candidate_rate_l
  = candidate_data_on_l / candidate_predicted_runtime

predicted_load_l
  = (existing_rate_l + candidate_rate_l)
  / predicted_effective_bandwidth_l
```

候选预测和 `update_link_loads()` 必须调用同一个底层汇总函数，避免两套公式再次分叉。

**验收标准**

- 新增“候选预测后接纳，再读取实际状态”的对照测试；
- 在不推进热度且使用同一带宽快照时，预测与实际链路负载误差小于 `1e-9`；
- 推进一个时隙后，差异只能来自文档中明确规定的热度更新，而非流量汇总公式不同。

### P0-03 IFS 的物理含义尚不足以支撑“推理准确性”主张

**当前表现**

节点基础 IFS 是经验先验，动态 IFS 使用：

```text
A_n(t+1)
  = clip(
      A_n^base · exp[-alpha_a · load_n' - beta_a · heat_n'],
      a_min,
      A_n^base
    )
```

DNN 级 IFS 再按节点承载 FLOPs 进行加权几何平均。

**代码依据**

- 参数：`core/environment.py:39-49`
- 候选节点 IFS：`core/environment.py:706-718`
- DNN 级聚合：`core/environment.py:745-761`
- 默认先验：`core/topology.py:211-224`

**核心问题**

普通资源竞争通常直接影响排队和执行时延，并不必然改变一个确定性 DNN 的输出准确率。若没有进一步建模软错误、近似计算、量化、早退、丢包、降频导致的超时截断或模型版本差异，仅依据 CPU 负载降低“推理准确性”缺少充分物理依据。

本项目又明确不对具体 DNN 和数据集建模，因此无法直接用 Top-1 accuracy、mAP 等任务指标验证当前 IFS。

**推荐修复**

采用与抽象 DAG 范围兼容的保守方案：

1. 保留名称 **Inference Fidelity Score, IFS**，中文统一为“推理保真性分数”；
2. 明确 IFS 是归一化的代理质量指标，不是具体数据集准确率，也不是单次推理成功概率；
3. 将基础先验解释为离线 profiling 或历史统计得到的“节点执行结果保持参考输出的能力”；
4. 将动态衰减解释为资源压力相关的输出完整性退化代理，并明确这是一项建模假设；
5. 在论文中给出参数校准方法；若没有真实 profiling 数据，至少给出宽范围敏感性分析；
6. 所有结果图、表和正文删除把 IFS 直接简称为 `accuracy` 的主展示字段，仅保留代码兼容别名；
7. 在局限性中声明：抽象 DAG 模型评估的是部署策略对代理质量的影响，不报告具体 DNN 的真实预测精度。

如果无法为“负载导致输出保真性降低”提供数据或文献依据，则应采用更严格的替代方案：

```text
IFS = 仅由离线节点/模型配置先验聚合得到；
负载只影响 OSS 和 delay，不直接影响 IFS。
```

**验收标准**

- 论文、README、代码注释和结果字段对 IFS 的定义一致；
- 不再出现“IFS 就是推理成功概率”或“IFS 就是模型准确率”的表述；
- 给出至少一组 IFS 参数敏感性或校准实验；
- 给出 IFS 与实际代理事件之间的可操作定义，例如输出校验通过率、数值误差保持率或无软错误执行率。

### P0-04 新语义版本缺少完整的正式实验结果

**当前表现**

代码已标记：

```text
objective_semantics_version
  = stability_fidelity_v2_return_energy
```

实验框架已经支持多随机种子、敏感性、消融、Pareto、规模和偏好实验，但当前代码回归测试不能替代正式实验。旧连乘可靠性或未计回传能耗的结果不能与新版结果混合。

**影响**

- 无法证明算法在新版目标下仍优于基线；
- 无法证明改进来自定制化算子，而非随机波动；
- 无法证明 OSS/IFS 不只是重复表达同一负载变量；
- 无法支撑高水平论文要求的结果可靠性和可复现性。

**推荐实验最小集**

| 实验 | 必须报告的内容 |
| --- | --- |
| 主对比 | 所有算法在相同场景、相同请求流和配对随机种子下的四目标、接纳率和运行时间 |
| 多次重复 | 均值、标准差或 95% 置信区间；建议至少 20 个配对种子 |
| 显著性 | 配对 Wilcoxon 或满足条件时的配对 t 检验，同时报告效应量 |
| 消融 | DAG 感知初始化、块交叉、偏斜变异、精英局部搜索、动态 ε 约束、角色化子膜 |
| 敏感性 | `alpha/beta/lambda`、上下界、OSS 聚合权重、种群规模、迭代次数、变异概率 |
| 相关性 | OSS 与 IFS 的 Pearson/Spearman 相关系数、散点图和目标冲突率 |
| Pareto | HV，并建议增加 IGD+ 或 epsilon indicator；所有方法使用同一归一化参考 |
| 规模 | 节点数、DAG 任务数、请求数增长下的性能和运行时间 |
| 一致性 | 候选预测值与接纳后下一状态实际值的误差分布 |
| 收敛 | 代际 HV/最佳满意度/可行解比例和墙钟时间 |

**验收标准**

- 所有正式结果行均带新版 `objective_semantics_version`；
- 原始结果、汇总结果、绘图输入和图表可由脚本重新生成；
- 旧版本结果单独归档，不进入新版统计；
- 结论同时报告统计显著性和实际效应大小；
- 测试机器、运行时间、依赖版本和随机种子可追踪。

## 5. P1：模型说服力与实验可信度问题

### P1-01 `remaining_slots` 在接纳后固定，运行期间不响应带宽变化

**当前表现**

接纳时执行：

```text
remaining_slots = ceil(estimated_delay / slot_length)
```

之后每个时隙固定减 1。即使有效带宽因并发负载和热度变化，任务完成时间也不会调整。

**代码依据**

- `proposed.py:411-424`
- `core/environment.py:822-838`

**推荐处理**

投稿前至少明确采用“接纳时固定服务时长的流体近似”。此时 `estimated_runtime` 是资源占用期限，动态带宽只影响后续请求看到的环境，不追溯修改已接纳请求的完成时间。

若论文希望宣称真实模拟执行进度，则需要改为维护剩余计算量和剩余通信量，并根据每时隙实际服务率推进；该方案改动较大，不建议与 P0-01 同时扩展，除非论文创新点明确包含在线执行仿真。

**验收标准**

- 论文和系统模型明确选择“固定服务时长”或“剩余工作量推进”之一；
- 不再同时使用两套含义；
- 若保留固定时长，增加局限性说明。

### P1-02 OSS 与 IFS 可能高度相关，四目标存在信息重复

**当前表现**

OSS 和 IFS 的节点部分都由：

- 节点基础先验；
- 同一个预测负载；
- 同一个预测热度；
- 相似的指数衰减形式

共同决定。两者虽然参数不同，仍可能在实验中近似单调相关。

**影响**

- “四目标优化”可能在实质上接近三目标优化；
- 论文难以证明运行稳定性与推理保真性是两个独立权衡；
- Pareto 前沿可能因目标冗余而虚增维度。

**推荐修复**

- 报告每个场景下 OSS/IFS 的 Pearson 和 Spearman 相关系数；
- 报告二者目标冲突率，即一个目标改善而另一个恶化的候选对占比；
- 分别进行“去掉 OSS”和“去掉 IFS”的目标消融；
- 通过不同先验来源或不同驱动机制增强区分：
  - OSS 由节点/链路状态、负载和历史压力决定；
  - IFS 由执行配置或输出完整性 profiling 先验决定；
- 若长期相关系数接近 1，应合并目标，或将 IFS 改为约束而非独立优化目标。

**验收标准**

- 论文给出 OSS/IFS 区分效度证据；
- 对高相关结果进行解释，不隐瞒目标冗余；
- 四目标相对三目标的收益由消融实验支持。

### P1-03 质量先验和动态系数主要是经验设定，缺少校准依据

**当前表现**

默认节点先验大多随机分布在约 `[0.94, 0.99]`，动态参数和截断下界由代码常量给出，例如：

```text
alpha_r = 0.8, beta_r = 0.5
alpha_a = 0.5, beta_a = 0.3
alpha_l = 0.7, beta_l = 0.4
o_min = a_min = l_min = 0.5
```

**代码依据**

- `core/environment.py:38-55`
- `core/topology.py:211-224`

**风险**

- 结果可能由人为参数范围主导；
- `0.5` 下界可能造成高负载场景中的分数饱和，削弱算法区分能力；
- OSS 的节点/链路权重 `0.5/0.5` 缺少依据。

**推荐修复**

- 把所有质量参数纳入场景配置和结果元数据；
- 明确先验来自测量、文献、公开 trace，还是受控合成设定；
- 对衰减系数、EMA 系数、下界和聚合权重做全局敏感性分析；
- 绘制分数分布和触底比例；
- 至少提供“弱退化、默认退化、强退化”三类场景；
- 若无真实数据，正文使用“synthetic but controlled”表述，不宣称参数代表真实平台。

**验收标准**

- 任何论文表格结果都能追溯到完整参数配置；
- 默认参数位于稳定敏感性区间，而非性能峰值的单点；
- OSS/IFS 触底比例得到报告；
- 更换合理参数后，算法排序和主要结论不发生无解释反转。

### P1-04 固定路由与动态带宽的关系需要明确

**当前表现**

所有节点对路径在环境初始化时按基础带宽构建并缓存，后续有效带宽变化不会触发重路由。

**代码依据**

- `core/environment.py:176-201`
- `core/environment.py:392-397`

**推荐处理**

保留固定路由是合理且更易复现的范围选择，但必须说明：

- 控制器只优化计算部署，不优化路由；
- 路由由底层网络预先确定；
- 动态带宽只改变固定路径上的传输时延和负载；
- 结论不等价于联合任务部署—路由优化。

可增加一个“小规模动态最短路”对照实验，证明固定路由不会改变主要算法排序，但不要求把动态路由加入主算法。

**验收标准**

- 系统模型、算法输入和局限性均明确固定路由假设；
- 图表和标题不使用“joint routing”或同义表述。

### P1-05 全双工物理链路采用双向负载最大值，需给出容量语义

**当前表现**

共享物理链路负载定义为：

```text
load_physical = max(load_forward, load_reverse)
```

**代码依据**

- `core/environment.py:425-444`

**推荐处理**

明确每个方向拥有独立容量，因此采用 `max` 表示共享故障和热度域下的最繁忙方向压力。如果实际假设是半双工或共享总容量，应改为双向 offered rate 之和。

建议增加配置项：

```text
duplex_mode = "full" | "shared"
```

并在敏感性实验中至少比较一次 `max` 与 `sum`。

**验收标准**

- 论文给出明确的容量和故障域解释；
- 输入上传与结果回传不会因双向边表示而重复计算同一个物理故障事件。

---

### P1-06 能耗满意度参考边界较松，可能压缩目标差异

**当前表现**

能耗下界主要由逐任务最小计算能耗构成，未计不可避免的通信下界；上界由每段传输独立取最大路径能耗构造。这是一组算法无关的安全参考边界，但不一定紧。

**风险**

- 能耗满意度可能集中在很窄区间；
- 能耗目标在 Pareto 排序或最终偏好选择中的实际作用变弱；
- 不同规模场景的能耗满意度可比性有限。

**推荐修复**

- 保留原始 `total_energy` 作为主报告指标；
- 报告 `energy_satisfaction` 的分布、极差和方差；
- 用小规模穷举或随机大样本估计边界松弛度；
- Pareto 图中的归一化应使用同一场景、所有算法联合得到的参考范围，并防止测试数据泄漏到算法搜索内部；
- 若满意度长期集中，可使用场景级固定物理预算或更紧的可行上下界。

**验收标准**

- 能耗敏感偏好能够稳定改变最终选解；
- 能耗目标消融能产生可解释变化；
- 不只报告归一化满意度，同时报告原始能耗及单位。

---

### P1-07 主算法与 RTBL 基线的可见状态和优化语义不完全对称

**当前表现**

主算法在候选评价和算子中使用连续节点/链路负载、热度、有效带宽、OSS 和 IFS。RTBL 决策主要使用：

- 当前二值可用性；
- 历史可用性估计；
- 节点当前 IFS 兼容字段；
- 逐任务时延代价。

RTBL 没有使用与主算法同粒度的链路稳定性和候选后状态。

**代码依据**

- `rtbl/scheduler.py:34-83`
- `rtbl/scheduler.py:130-149`
- `proposed.py` 中的候选评价与 DAG 感知算子

**推荐处理**

不要为追求形式一致而改变已发表基线的核心算法。应当：

- 区分“所有算法共同可观察的环境状态”和“某算法是否利用该状态”；
- 保留 RTBL 原始决策机制，同时使用统一后验评价器报告四项目标；
- 增加一个“信息增强 RTBL”或简单贪心基线，使用与主算法相同的状态但不使用进化搜索；
- 明确性能差距有多少来自状态利用能力、有多少来自搜索策略。

**验收标准**

- 所有算法面对完全相同的请求、拓扑、初始状态和随机轨迹；
- 论文表格列出每个基线使用的信息；
- 至少一个强基线能够访问与主算法相同的状态信息。

### P1-08 缺少预测值与实际下一状态的一致性验证

现有单元测试主要验证公式、边界、聚合方式和非变异性，还不足以证明候选预测器在动态环境中准确。

**建议新增测试**

1. 保存环境快照；
2. 对候选调用统一预测；
3. 实际接纳同一候选；
4. 按规定推进到预测对应的时间点；
5. 比较节点负载、链路负载、热度、有效带宽、OSS、IFS 和 delay；
6. 恢复环境并对多组随机候选重复。

**验收标准**

- 每个状态量都有明确的预测时点；
- 对确定性相同公式，误差接近数值精度；
- 对近似量，论文报告 MAE、MAPE、最大误差及误差来源。

## 6. P2：建议进行的工程整改

### P2-01 建立显式的算法观测快照

当前算法直接访问 `Environment` 内多个对象字段，算法可见状态和仿真器内部状态的边界不够清楚。

建议建立只读 DTO：

```text
ObservationSnapshot
  slot
  node_available_cpu
  node_load
  node_heat
  node_base_oss
  node_base_ifs
  link_load
  link_heat
  link_effective_bandwidth
  link_base_stability
  fixed_routes
```

环境私有信息可包括：

- 下一时隙随机故障结果；
- 未发生的未来请求；
- 随机数生成器内部状态；
- 真实但未观测的故障原因。

这样可以在论文中准确描述在线算法的信息结构，并防止未来代码无意使用未来信息。

当前仍保留 `o_reliability`、`a_reliability`、`accuracy`、`operation` 等兼容接口。短期兼容合理，但长期容易使论文语义回退为“成功概率/准确率”。

建议：

- 新增代码只使用 `operational_stability` 和 `inference_fidelity`；
- 兼容属性标记为 deprecated；
- 正式 CSV 主字段仅展示新名称；
- 在后续主版本删除旧命名。

## 7. 推荐的统一模型语义

完成整改后，建议论文统一采用下列解释：

### 7.1 运行稳定性 OSS

OSS 是候选部署在预测接纳后状态下的**归一化运行稳定性效用**。它由唯一节点域和唯一物理链路域的状态相关质量分数分层聚合得到。

OSS：

- 不是严格的端到端成功概率；
- 不应与所有组件无故障概率的原始连乘混用；
- 可以用于候选排序、Pareto 优化和敏感性分析；
- 必须由参数校准和实验证据支撑。

### 7.2 推理保真性 IFS

IFS 是抽象 DAG 在所选执行节点上保持参考输出质量的**归一化代理分数**。它按各节点承载的计算量加权聚合。

IFS：

- 不等于具体数据集上的分类准确率；
- 不等于单次推理成功概率；
- 先验来自离线 profiling、历史校验或受控合成场景；
- 动态退化机制必须有明确假设和敏感性证据。

### 7.3 时延

时延是基于统一候选预测快照得到的端到端估计：

```text
输入上传
  + DAG 关键路径计算与中间通信
  + 结果回传
```

固定路由下使用候选接纳后的预测有效带宽。

### 7.4 能耗

能耗采用部署级确定性一阶模型：

```text
总能耗
  = 节点计算能耗
  + 输入上传能耗
  + DAG 中间传输能耗
  + 结果回传能耗
```

若不考虑负载相关功耗，应明确 `comp_power` 和 `energy_per_mb` 是平均系数；能耗不需要伪装成动态预测量。

### 7.5 四目标

统一优化向量为：

```text
F(x)
  = [
      IFS(x | predicted_state),
      OSS(x | predicted_state),
      delay_satisfaction(x | predicted_state),
      energy_satisfaction(x)
    ]
```

四个目标全部最大化，同时保留原始时延和原始能耗用于结果解释。

## 10. 最终判定标准

可将当前模型的投稿就绪状态划分为：

| 状态 | 判定条件 |
| --- | --- |
| 研究原型 | 算法可运行、单元测试通过，但核心模型论证和正式实验未完成 |
| 可投稿 | 全部 P0 完成，主要 P1 有证据，正式实验和复现材料完整 |
| 高水平投稿就绪 | 除上述条件外，IFS 构念有可信依据、目标区分效度明确、强基线与统计证据充分 |

当前项目处于“**成熟研究原型，但需要大修后投稿**”阶段。最优先的工作不是继续增加遗传算子，而是先闭合候选状态预测、明确 IFS 的学术含义，并使用新版语义重新建立完整实验依据。
