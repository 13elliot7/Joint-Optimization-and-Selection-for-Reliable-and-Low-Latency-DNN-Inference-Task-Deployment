# Proposed 算法运行瓶颈与修改方案

## 1. 背景

当前 `proposed` 算法已经从“静态部署后立即结束”改成了“单个 DNN 先搜索部署方案，接纳后注册为运行块，再按 time slot 推进系统状态”的动态流程。

当前主流程位于：

- `proposed.py`
  - `run_proposed()`
  - `cross_over1()`
  - `dominated_sort()`
  - `get_res()`
  - `update_res()`
- `core/environment.py`
  - `_evaluate_assignment()` 间接依赖的动态可靠性与时延估计接口
  - `estimate_delay_from_assignment()`
  - `advance_time_slot()`

本文件只分析 **当前版本** 的主要运行瓶颈，并给出后续改造建议。

## 2. 当前执行流程概览

单个 DNN 在 `run_proposed()` 中的执行过程可以概括为：

1. 打印当前待接纳 DNN 信息
2. 初始化种群与搜索状态
3. 若为首代，则构造首代父代种群
4. 复制父代到 `P+Q`
5. 通过 `cross_over1()` 生成子代
6. 对 `P+Q` 全体候选计算三目标值
7. 通过 `dominated_sort() + get_res() + update_res()` 产生下一代父代
8. 重复多代搜索
9. 对保留父代做最终选解
10. 接纳成功则注册为 `running_dnn`
11. 推进一个 time slot

因此，算法耗时主要可能来自五个阶段：

1. 首代初始化
2. 交叉生成子代
3. 候选解评价
4. 非支配排序与拥挤距离计算
5. 时隙推进

## 3. 当前主要运行瓶颈

### 3.1 首代初始化是第一大热点

首代种群初始化仍然依赖大量随机试探，尤其包含两类高成本循环：

1. `pop_size - 3` 个随机资源可行解的逐任务构造
2. 最后两个“尽量满足时延约束”的种子个体搜索

其中：

- 随机资源可行解部分对每个任务都设置了最长 `10s` 的采样窗口
- 最后两个时延种子共享一个 `20s` 搜索窗口
- 每次时延可行性判断都要调用 `check_delay_random()`

这会导致：

- 即使 `iteration_limit` 很小，算法也可能在首代阶段停留很久
- 单个 DNN 的总耗时往往主要消耗在首代种群构造，而不是后续 slot 推进

### 3.2 交叉阶段仍然存在高开销的可行性搜索

虽然 `cross_over1()` 已经修正为：

- 不再原地污染父代
- 一次交叉生成两个独立子代
- 两个子代分别变异后写入 `P+Q`

但它内部仍然采用“随机尝试直到找到可行交叉，否则超时回退”的方式。

当前特点：

- 每次 `cross_over1()` 最长可运行 `10s`
- 每次尝试都需要：
  - 复制父代
  - 构造两个子代
  - 分别做 `_is_assignment_valid()`
- `_is_assignment_valid()` 内部又会构建二维矩阵并调用 `env.check_resource()`

因此在可行交叉难找时，交叉阶段会成为第二大热点。

### 3.3 候选解评价仍然偏重，关键成本在时延估计

当前已经引入 `count_values()`，把原来的：

- `count_values1()`
- `count_values2()`
- `count_values3()`

合并成了对同一候选解只做一次 `_evaluate_assignment()`。

这一步已经明显减少了重复计算。

但单次 `_evaluate_assignment()` 仍然包含：

1. `count_dynamic_accuracy_by_assignment()`
2. `count_dynamic_operation_by_assignment()`
3. `estimate_delay_from_assignment()`

其中最重的是 `estimate_delay_from_assignment()`，因为它仍然复用旧的静态时延模型：

- `count_delay_random()`
- `count_tran_random()`

该部分需要递归遍历 DNN DAG，并多次查找任务依赖与传输路径，因此单次评价成本仍然偏高。

### 3.4 最终选解阶段仍有一轮整群重复评价

在多代搜索结束后，`run_proposed()` 会再次对保留下来的父代种群做一轮完整 `count_values()`。

这意味着：

- 即使每代内已经算过一轮候选解目标值
- 最终选择前仍然会对 `pop_size` 个个体再完整评估一次

这部分不是最重的瓶颈，但属于稳定存在的重复成本。

### 3.5 非支配排序与拥挤距离计算是中等固定成本

当前：

- `dominated_sort()` 采用两两比较的非支配排序
- `get_res()` 已修正为按 Pareto 层分别计算拥挤距离
- `update_res()` 再根据 `rank + distance` 生成下一代

这部分的复杂度主要来自：

- `dominated_sort()` 的 `O(N^2)` 支配关系构建
- `get_res()` 在每个 Pareto 层上按三个目标排序

在当前 `2 * pop_size = 120` 的规模下，这部分仍可接受，但它属于稳定存在的固定成本。在前面几个热点下降后，它会变得更突出。

### 3.6 时隙推进不是主瓶颈

`advance_time_slot()` 当前主要执行：

1. 重算节点与链路占用
2. 更新热度
3. 刷新动态可靠性
4. 扣减 `remaining_slots`
5. 释放完成 DNN

这一部分主要是对：

- 节点集合
- 链路集合
- `running_dnns`

做线性遍历，因此相较于搜索阶段的随机试探与时延递归，slot 推进不是主耗时来源。

## 4. 当前瓶颈的优先级排序

按影响程度，当前 `proposed` 的运行瓶颈可以排为：

1. 首代初始化中的随机可行解搜索
2. `cross_over1()` 中的可行性交叉搜索
3. `_evaluate_assignment()` 内部的 DAG 时延估计
4. 最终选解阶段的重复整群评价
5. `dominated_sort() + get_res() + update_res()` 的固定筛选成本

## 5. 修改方案

### 5.1 第一优先级：收紧首代初始化搜索成本

目标：快速降低单个 DNN 的等待时间。

建议：

1. 缩小每个任务的 `10s` 随机采样窗口
2. 缩小最后两个时延种子的 `20s` 搜索窗口
3. 给首代增加更多启发式初始化，而不是主要依赖随机试探

可选启发式：

- 全云解
- 本地优先解
- 最大资源优先解
- 发起节点附近优先解

预期效果：

- 首代构造更稳定
- 减少极端长时间卡在初始化阶段的情况

### 5.2 第二优先级：降低 `cross_over1()` 的可行性交叉开销

目标：避免每次交叉都长时间随机碰撞。

建议：

1. 缩短 `cross_over1()` 的超时上限
2. 增加最大尝试次数而不是单纯按时间控制
3. 交叉失败时更快回退到“父代复制 + 独立变异”
4. 优先在合法节点集合中选取交叉或变异候选

更进一步的做法：

- 先预构建当前 DNN 每个任务的候选合法节点集合
- 交叉后只在合法集合中做修复

预期效果：

- 降低交叉阶段的最坏耗时
- 减少大量无效可行性检查

### 5.3 第三优先级：继续降低候选解评价成本

目标：减少 `_evaluate_assignment()` 的调用代价。

建议：

1. 对同一代内重复出现的 assignment 做缓存
2. 为 `estimate_delay_from_assignment()` 增加轻量缓存
3. 对 `_build_assignment_matrix()` 结果复用，避免重复构建

进一步优化方向：

- 减少 `count_delay_random()` 中的重复前驱查询
- 预计算 DAG 前驱关系
- 预计算任务索引映射，避免多次 `tasks.index(...)`

预期效果：

- 降低大规模候选评价时的固定成本
- 提高单代搜索吞吐量

### 5.4 第四优先级：减少最终选解阶段的重复评价

目标：避免进化结束后再对整群做一次完整重算。

建议：

1. 在代内评价后保留父代个体的最新目标值
2. 最终选择时直接复用缓存
3. 只有在确实需要时才对最终 best assignment 重新计算一次 `delay`

预期效果：

- 减少 `pop_size` 级别的重复评估
- 保持最终输出口径不变

### 5.5 第五优先级：优化非支配排序实现

目标：压低稳定存在的筛选成本。

建议：

1. 保持当前 `get_res()` 正确版本不变
2. 优化 `dominated_sort()` 的实现方式
3. 在 `pop_size` 固定时减少不必要的全矩阵重复构造

说明：

这部分当前不是第一瓶颈，因此不建议优先动大结构。应在初始化、交叉、评价成本下降后再处理。

## 6. 建议的修改顺序

推荐按以下顺序推进：

1. 调整首代初始化超时和启发式初始化
2. 调整 `cross_over1()` 的超时与回退策略
3. 为 assignment 评价增加缓存
4. 减少最终选解阶段重复评价
5. 再处理 `dominated_sort()` 的实现优化

## 7. 当前代码层面的注意点

### 7.1 `iteration_limit=0` 的语义需要重新确认

当前 `run_proposed()` 使用：

```python
while index < self.iteration_limit:
```

这意味着：

- `iteration_limit=0` 时不会进入进化循环
- 首代初始化也不会发生

如果希望 `0` 表示“只跑首代”，则这一行为需要重新定义。

### 7.2 日志条件存在一个死分支

当前：

```python
if index == 0 or index == self.iteration_limit or index % 10 == 0:
```

但循环条件是 `< self.iteration_limit`，因此：

- `index == self.iteration_limit` 不会触发

这不影响性能，但说明日志条件还可以顺手整理。

## 8. 总结

当前 `proposed` 的主要问题不是动态环境本身，而是“搜索阶段仍然过重”。

更准确地说：

- **最耗时的是随机试探**
- **其次是可行性交叉**
- **再次是基于 DAG 的时延估计**

因此，后续优化应优先围绕：

1. 减少随机搜索时间
2. 提高交叉成功效率
3. 降低单次评价成本

而不是优先优化 time slot 推进逻辑。
